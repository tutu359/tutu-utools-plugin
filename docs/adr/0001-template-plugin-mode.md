# 0001 - 工具箱采用 uTools 模板插件模式而非自定义 React 界面

日期：2026-08-30　状态：已接受

## 背景

tutu 工具箱最初以自定义 React 界面（uTools 标准 `main` 页面）实现：哈希计算是「左输入右结果」布局，快速 Shell 有页内输入框与下拉结果区。维护者在真机试用后明确表示期望的交互是 uTools 原生的「标签页 + 继续在搜索框输入」形态：输 `sh` 回车后搜索框挂着工具标签，命令继续在搜索框里敲，结果直接显示在搜索框下方的列表里。

uTools 官方「模板插件应用」机制（`window.exports` 的 list 模式）正是这种体验的官方实现，但官方规定：**模板模式与自定义插件界面（`main` 字段）互斥，二者只能选一**。此外，7.x 真机验证发现：regex 匹配指令对「键入文本」的呈现不可靠，而模板列表模式的 `search` 回调天然支持在子输入框中实时交互。

## 决定

- 整个插件采用模板插件模式：删除 `plugin.json` 的 `main` 字段，所有工具以 `window.exports["<code>"]` 的列表模式（`mode: "list"`）实现于 `preload.js`；
- 工具的交互统一为：关键字进入 → 挂标签 → 在搜索框输入 → 列表实时反馈 → 回车选择执行；执行结果（含 stdout/stderr/退出码）以列表条目展示；无输出的命令执行后直接隐藏主窗口；
- 放弃 React 自定义界面（React 源码保留在仓库中不再使用），自动化测试的缝从「渲染界面组件」改为「以 vm 加载 preload、驱动 `window.exports` 处理器」；
- 「加新工具」流水线相应调整为：在 `preload.js` 增加一个模板处理器 + 在 `plugin.json` 增加一条 feature。

## 补充（真机复查后修正理由，决定不变）

初版理由中的「标签页体验只有模板模式才能实现」不成立：自定义界面插件同样可以通过 `setSubInput` 获得搜索框标签页与框内打字（官方「插件应用市场」即为主界面 + 子输入框并存的真实案例）。真正的分水岭是**回车语义**：子输入框在自定义界面下没有「回车」事件，打字只能逐字流回页面；而本插件两个工具的核心动作都是「敲完回车」（shell 回车执行、hash 回车复制），「回车 = 选中条目」只有模板列表模式的 `select` 回调提供。故决定不变：模板模式是唯一能同时满足标签页输入与回车语义的官方机制。

## 后果

- 正面：UX 与官方插件完全一致；代码量显著减少；不再有 preload 与页面两层的桥接问题；「工具即函数」降低后续补功能的成本。
- 负面：未来若出现真正需要复杂自定义界面的工具，本插件无法再启用 `main`，届时只能为该工具单独开第二个插件；React 相关依赖与代码成为仓库中的闲置历史。
- 依据的真机事实：uTools 7.8.0（维护者环境）在 preload 加载上参考最近 `package.json` 的 `type` 字段，故 `dist/` 必须携带 `type: "commonjs"` 的 `package.json`（详见 README 关键约定）。

# 真机踩坑与教训清单

本文件记录 tutu 工具箱开发过程中**实际踩过、并已验证根因**的坑。改动本插件前先通读 —— 每一条都对应一次真实的返工，不要重蹈覆辙。

> 使用方式：改代码前扫一遍「防再犯守则」；遇到新的真机怪象，先来这里对照，再动手修。修复某个问题时，把新教训追加到本文件对应章节。

## 1. uTools 基座的真机事实（7.8.0 验证）

这些是官方文档没写清、但真机实测确认的行为，**代码必须与它们兼容**：

### 1.1 preload 加载参考最近 `package.json` 的 `type` 字段

- 现象：根 `package.json` 声明 `"type": "module"` 时，preload **静默加载失败**（`window.services` 不存在，页面能开但全部功能无响应，无任何报错）。
- 修复：`dist/` 必须携带 `{"type": "commonjs"}` 的 `package.json`（由 `public/package.json` 构建时复制）。
- 教训：**最新版 Electron 文档说「preload 忽略 type 字段」，不代表定制内核如此**。遇到「preload 静默死亡」，先怀疑构建产物环境，再怀疑代码。
- 排查利器：页面里放一条「诊断条」（显示 services/utools 存活状态与错误消息），比翻控制台快得多。

### 1.2 匹配指令的正则必须斜杠包裹

- regex 的 `match`、over 的 `exclude` 必须写成 `"/^xxx$/"`（正则字面量格式），**裸模式**（`"^xxx$"`）不被解析，入口**静默失效**（列表里永远不出现，无任何报错）。
- 依据：官方 plugin.json 文档所有示例均为斜杠字面量格式。

### 1.3 子输入框的 search/select 事件固定派发给「进入时的 feature 处理器」

- 模板列表模式下，从 feature A 进入后，**所有** search/select 事件永远派发给 A 的处理器 —— 在 select 回调里手动调用 feature B 的 enter「换列表内容」是**假切换**：列表数据变了，但后续打字/回车事件仍派发给 A（表现为打字清空列表、回车行为错乱）。
- 正确做法：A 充当**事件路由器**，维护「当前激活工具」状态，把 search/select **转发**给当前工具的处理器；enter 时重置状态。
- 教训：**这类「事件派发给谁」的底座行为无法靠单测覆盖**（测试直接驱动处理器会绕过路由），必须真机验证。本清单 §2 的测试缝盲区即由此而来。

### 1.2b 相关：「跳转」类 API 的实测语义

- `redirect(label)` 的 label 按「指令名称」查找：**功能指令的名称 = 关键字**（`hash`/`sh`），传中文名称会错位命中匹配指令的 label 或无指令可匹配；
- redirect 后指令被重新填入搜索框，**用户需要再回车一次** —— 它是「跳转入口」，不是「直达工具」；
- 同插件内切换工具的正确做法：**在事件路由器里委托**（见 §2.4），或让工具自己成为关键字入口。

## 2. 代码级教训（每条都发生过）

### 2.1 「假切换」：换列表数据 ≠ 换事件路由

在 select 回调里手动调用另一个工具的 enter 换掉列表数据，底座的事件派发**不会**跟着走。任何「列表原地切换成另一个工具」的实现，必须同时保证后续 search/select 被正确路由（toolbox 的路由器模式，见 preload.js 的 `state.currentTool`）。
**教训：测试直接驱动处理器函数时，会绕过「底座把事件派发给谁」这个事实 —— 测试全绿 ≠ 真机正确。真机行为必须实测。**

### 2.2 空列表不是合法的「等待输入」状态

sh 从首页进入且无命令时返回 `[]`，用户面对一片空白（placeholder 还停在首页的文案），完全不知道该干嘛。**列表模式的列表永远不应为空** —— 没有可执行条目时给引导条目（如「输入命令」提示行）。
**教训**：用户看到的「空白」就是 bug，哪怕逻辑上「等输入」说得通。

### 2.3 数组双包

`shellHintItem()` 返回数组、调用处又包一层 `[shellHintItem()]` → 列表变成嵌套数组，渲染异常。工具函数返回**单个条目对象**，调用处决定是否包裹。

### 2.4 分支条件要按「用户可见结果」设计，不能照搬旧实现的布尔表达式

「无输出且成功 → 静默收工」曾被写成 `exitCode !== 0 || lines.length === 0`（从旧 React 版迁移时照搬），导致 `true` 命令也弹「退出码 0」。三种结果（有输出 / 无输出成功 / 无输出失败）各自分支写清楚，不合并条件。

### 2.5 用 python/sed 批量改名会误伤函数体

批量重命名参数（如 `action` → `_action`）时，函数**体内**对该参数的引用一并被替换 → `ReferenceError`。批量替换后必须 grep 函数体内对原名的引用。

### 2.6 测试断言要与异步时序对齐

select 触发异步执行（child_process promise）后**同步断言**，必然竞态失败。等待 promise 或 `waitFor` 后再断言。

### 2.8 preload 拆文件后的两个模块加载事实

- preload 内部 `require("./tools/xxx.js")` 相对 **preload.js 自己的位置**解析（真机与 node 测试都需要把 require 基准指向 preload.js 所在目录，否则工具模块静默加载失败）；
- 工具模块经 Node require 加载后，作用域里**没有 window 全局**（真机 preload 领域有，测试的 node require 没有）—— 工具模块不能直接摸 `window.utools`，平台 API 必须由装配层以懒函数注入，事件触发时才解引用。

### 2.7 测试替身要覆盖被测代码用到的全部 API

假 `window.utools` 缺 `setSubInputValue` 时，真机功能正常但测试崩；反过来，测试通过 ≠ 真机通过（§1.3 的假切换就是「测试绕过了底座事件派发」的盲区）。**测试绿了仍需真机冒烟**，尤其是涉及底座派发行为的改动。

## 3. 排查此类问题的固定动作

1. **先复现再修**：用 node 直驱 preload（vm + 假 utools 记录调用）走一遍用户路径，能复现的不猜；
2. **页面放诊断**：preload 存活状态直接显示在列表条目上（诊断条），别让用户翻控制台；
3. **底座派发规则以真机为准**：文档没写的行为（事件绑定时机、redirect 的二次回车），以用户真机观察为准，修改后做最小对照实验；
4. 官方文档是第一信源，但**最新版文档 ≠ 用户内核行为**（preload type 字段案例），定制内核的差异要真机验证。
